# 本地 Android MVP 开发与验证

## 固定工具版本

- Kotlin 2.1.20，Android Gradle Plugin 8.9.2，Gradle 8.11.1。
- JDK 21（本次环境 Temurin 21.0.13+9），compileSdk/targetSdk 35，Build Tools 35.0.0，minSdk 26（Android 8.0）。
- 原生 Android Activity / View、SQLiteOpenHelper；纯 Kotlin `core` 模块独立测试，无云服务、联网权限或运行期 JSON 第三方依赖。
- 测试依赖 JUnit 4.13.2、Gson 2.12.1，仅测试读取仓库合成 JSON；Android 测试使用系统旧测试 runner（只用于 smoke test）。
- 版本选择依据：[AGP 8.9 官方兼容表](https://developer.android.com/build/releases/agp-8-9-0-release-notes)。

## 构建

安装 JDK 21、Android SDK Platform 35 / Build Tools 35.0.0 / Platform Tools，接受 SDK 许可。

```sh
export ANDROID_HOME=/path/to/android-sdk
./gradlew :core:test :app:assembleDebug :app:lintDebug :app:assembleDebugAndroidTest
```

构建产物：`app/build/outputs/apk/debug/app-debug.apk`。仅供个人验收，debug 签名密钥自动建立于忽略的 `private/debug.keystore`，不随源码提交。不同环境重建签名可能不同；保留设备本地数据时需复用原密钥，不能直接卸载升级。

云环境的 JDK、SDK、Gradle 缓存和代理设置保存在 `/workspace/toolchains`，不在仓库。Java 工具需遵守会话代理和 CA；不要把本机代理地址或证书路径写进仓库。

## 工程分层

- `core/BocParser`：整条短信模板匹配，精确金额、日期校验和七类事件。未识别与非交易分开。
- `core/Accounting`：各币种统计，确认关联的退款/撤销只冲减原消费一次。手工关联校验账户、币种、累计金额，不自动猜测配对。
- `app/LedgerDb`：原文、提供方来源键、解析版本、人工覆盖、关联和操作历史。本地 SQLite；无删除短信或修改系统短信库行为。
- `app/SmsImport`：历史范围扫描、启动补扫、广播触发的延迟补扫。所有入库只从系统 Inbox 读取。
- `app/MainActivity`：权限、历史导入、筛选、原文、修正、关联、取消关联和独立演示账本。

## 来源、幂等和后台策略

来源键为带长度前缀的 `provider ID / sender / body / received milliseconds / sub_id` 的 SHA-256，另有 inbox/demo 命名空间。唯一索引确保同一提供方记录多次读取只保存一次；不同 provider ID 的同正文通知不会合并。SIM 与接收时间参与区分。短信库恢复/重建若更换本地 ID，不能保证跨恢复自动去重，不以金额或正文强行删除真实交易。

首次选择范围导入成功后启用补扫。启动和新短信唤醒都从成功水位前 24 小时扫描到当前时刻；只有完整查询成功才推进水位，半途中断已保存记录可以安全重扫。历史扩大范围是显式全范围扫描，后台不会自动读取首次选择起始日期之前的短信。

`SMS_RECEIVED` **只唤醒任务，不保存广播正文**。JobScheduler 延迟约 2 秒读取系统短信库，再做两次约 10 / 30 秒后的重扫，处理广播先于提供方入库的情况。不存在“广播事件”和“提供方事件”两份交易；系统 Inbox 对多段短信的拼接结果是唯一输入。相关 API：[Android Telephony.Sms.Intents](https://developer.android.com/reference/android/provider/Telephony.Sms.Intents)。

厂商系统的后台限制、短信权限限制、JobScheduler 时机和短信库插入延迟仍须真机验证。后台没有独立永久监听线程；应用被强行停止后通常需用户再次打开。收不到广播或短信库延迟超出重试窗口时，由下次打开补扫恢复。应用不充当默认短信应用，不申请发送/写短信权限。

## 记账与人工修正边界

- 借记卡转入、转出和支付默认用途待确认；明确分类为消费/收入之后才计入对应汇总。本人调拨/还款本金不计消费。
- 明确 95566 的记录默认进入正常解析；仅凭落款发现的其他号码记录仍保存，但来源待确认、不能计入汇总。用户可逐条确认来源。号码和落款并非银行身份的密码学证明。
- 原币 USD、SGD、JPY 和 CNY 分开；汇率只记录、不覆盖实际支付金额，不生成虚构的外币现金收入。
- 消费、撤销、退款都保留，默认没有自动关联。关联允许部分冲减，累计金额不能超过原消费；多个候选由用户核对，不自动选第一笔。
- 汇总采用**原消费归属口径**：关联的调整随原消费冲减。原消费未在筛选范围时，不在另一期间重复冲减；未关联退款单列，不计收入。列表日期筛选是短信接收日，正文日期单列；无法获知年份的月日仍保持未知。
- 分类和字段修正保留原解析结果与审计历史；可恢复原解析结果。重解析保留人工覆盖，有关联的记录冻结至用户先解除关联。排除统计也保留原文；有关联的记录先解除关联再修改/排除。
- 购汇还款作为双币种单事件保存：来源卡、实际 CNY 扣款、外币偿债、原始汇率。尚未实现与独立借记卡扣款通知的证据关联，也没有“已确认现金流合计”报表；疑似本金扣款默认待定，不自动当消费。不得将此限制描述为双通知已验证完成。
- 人工修正支持补全未知模板，需手动填写类型、卡尾号、币种、金额，可选正文日期/商户；购汇还款须填写来源卡和扣款金额。不反推短信未提供的银行入账状态。

## 数据与权限

应用没有 INTERNET 权限，数据库留在应用私有目录，禁用系统备份。没有埋点，也不记录短信正文日志。仓库与安装包只含合成演示样例；手机真实短信、数据库、密钥不得提交。

拒绝或撤销 READ_SMS 时，已有账目仍可查看，导入提示重新授权；RECEIVE_SMS 拒绝时可手动/启动补扫。某些安装器/系统会限制短信权限授予，必须实际核对系统设置。用户可从工具菜单停止后台补扫；已有数据保留。

演示使用独立 `demo.db`，主账本是 `ledger.db`。重复打开演示不复制样例。没有导出、数据库迁移旧版本、备份恢复、应用锁或额外数据库加密；卸载会删除本地账本。当前为首版调试验收包，不是已经完成所有真机验收的正式发布版。

## 最小真机验收（需用户实际授权设备操作）

1. Android 8.0+ 安装 debug APK，首次不授权，确认空账本和合成演示能正常打开。
2. 在演示中重复加载样例，仍为 16 条；按币种筛选，JPY 为 12345；信用卡退货单列；借记卡月日保留未知年份。
3. 把 SGD 2.50 撤销与对应消费关联，净额由 2.50 变 0.00；解除恢复。多笔同额时不能自动绑定，超额冲减应拒绝。
4. 人工修改字段/分类，重解析后保留，恢复解析后还原；原文和操作历史可见。
5. 切回手机账本，明确授予短信权限，导入一个小范围，重复导入条数不增加；强退并重启后仍存在。请勿将真实数据上传云端。
6. 检查未知模板/陌生发送方进入待确认而非消失；中行验证码、失败和还款提醒不生成交易。
7. 用设备端合成测试短信验证新短信、多段短信、双 SIM、广播后补扫不重复；撤销权限后可继续查看，重新授权后可补扫。
8. 在目标机型检查锁屏、后台限制、重启、强行停止后的恢复与长列表可读性；核对短信实际发送方和模板变体。
