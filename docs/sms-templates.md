# 中国银行短信模板与解析预期

## 当前状态与样本来源

已根据九条完整短信整理出七种模板形态，以及相应的预期字段。解析器和本地 Android 接入已按这些合成结构实现；覆盖只限严格匹配的样例格式，尚未完成真机验证。

完整结构用例位于 [boc-sms.json](../fixtures/synthetic/boc-sms.json)。卡尾号、商户、日期、金额、余额和汇率均替换为合成值，保持字段结构和需要验证的金额关系。此前的三个片段仅保留为金额示意。

输入仅有正文，没有短信接收时间、发送方号码及本地短信 ID。样本中的银行落款不能代替发送方校验；这些来源元数据需要在 Android 接入层获取。

## 七种模板

| 模板 | 关键文字 | 预期字段 | 分类边界 |
| --- | --- | --- | --- |
| 借记卡网上支付 | 网上支付支取人民币…交易后余额… | 借记卡尾号、月日、CNY 支出、交易后余额、渠道 | 用途与商户未知，可显示为未分类支付支出 |
| 借记卡跨行转入 | 收入(网银跨行)人民币… | 借记卡尾号、月日、CNY 转入、交易后余额、渠道 | “收入”说明账户流入，不直接证明经济收入 |
| 借记卡跨行转出 | 手机银行支取(跨行支付)人民币… | 借记卡尾号、月日、CNY 转出、交易后余额、渠道 | 不知道收款方，不直接判定消费或本人调拨 |
| 信用卡消费 | 在…消费…元 | 信用卡尾号、完整日期、商户、币种、金额 | 不推定结算币种、人民币金额及最终入账状态 |
| 信用卡撤销 | 在…撤销…元 | 信用卡尾号、完整日期、商户、币种、金额 | 保留事件，候选关联另行处理 |
| 信用卡退货 | 成功退货…元 | 信用卡尾号、完整日期、币种、金额 | 样本没有商户和原交易编号，不强行绑定原消费 |
| 信用卡购汇还款 | 购汇还款…购汇转出卡号…购汇转入…购汇转出…汇率… | 信用卡、来源借记卡、两种币种及金额、原始汇率 | 一笔还款含两个账户效果，不能压成单币种普通收支 |

0.1.1 在原模板中补充 TWD、HKD，不增加事件类型；[补充合成样例](../fixtures/synthetic/currency-variants.json)覆盖 TWD 千分位两位小数、HKD 普通金额和连字符商户，以及无效分组/精度/未知币种边界。每条样例表示独立短信，不新增拼接拆分行为。

## 金额与币种

- 所有金额使用精确十进制；JSON 中使用字符串，避免浮点中转。
- “人民币”和 RMB 在内部统一为 CNY，同时保留原文字样。
- 明确的 USD、SGD、JPY 优先于末尾的“元”。
- 合成例子 `JPY12,345元` 的金额是 JPY 12345。
- 金额分组先校验再去除逗号，例如 `12,34` 必须待确认，不能直接变为 1234。
- 全文中的逗号既可能是字段分隔符，也可能是金额千分位；不能先按逗号拆整条短信。
- 解析时使用正数金额和明确的事件类型表达方向，不把退货或撤销的负号混入原始金额。
- 余额金额的币种在这三种借记卡模板中由同条短信的人民币字段确定；保存这是模板上下文推得的币种。

## 日期与账户

借记卡正文只有月日，预期数据保存 `year: null`，不根据程序运行当天的年份补全。后续可依据真实接收时间和明确的跨年规则推断年份，并标记推断来源；原始月日必须保留。

信用卡正文有完整日期，但没有具体时分秒。交易时间与接收时间分别保存，不给当天交易虚构顺序或时区。

卡尾号仅作账户线索，不作全球唯一主键。账户需结合银行、借记/信用卡类型及用户的账户映射确认。购汇还款正文中同时出现信用卡尾号和来源借记卡尾号，两者角色不可交换。

## “收入”与“消费”的边界

`收入(网银跨行)` 可以确认资金进入借记卡，但无法从正文分辨工资、他人付款、退款或本人从另一账户转入。先保存转入事实，经济分类待确认。

同理，`手机银行支取(跨行支付)` 表示资金转出，不足以确定是本人账户调拨还是付款。即使另一端银行不接入首版，也允许手动标记本人调拨，避免虚增收入和支出。

## 撤销与退货分开记录

- 撤销保留 `credit_reversal` 类型；“成功退货”保留 `credit_refund` 类型。
- 消费与撤销在相同信用卡、日期、商户、币种、金额下形成候选；缺少原交易编号时不能宣称必然对应。
- 多个候选时保留待确认，支持手动关联和解除关联。
- 退货原文即使没有商户和原消费，仍可直接保存为退款记录并单独展示；不把它当成普通收入。
- 后续确认来源消费时再关联、继承分类或重算相关消费净额，不能又记退款、又另减一次原消费而在总账中扣减两遍。
- 保存退款发生日和原消费日，后续月度报表明确选择按退款发生期展示，或按原消费归属期重算；不能无提示改写历史。

## 购汇还款：一个事件、两个账户效果

合成示例：

```text
您的信用卡2222于2026年06月09日购汇还款，购汇转出卡号1111，购汇转入USD100.00，购汇转出RMB680.00，汇率0.147059【中国银行】
```

应保存以下信息：

| 字段 | 值 |
| --- | --- |
| 来源账户 | BOC 借记卡尾号 1111 |
| 来源资金减少 | CNY 680.00 |
| 还款目标 | BOC 信用卡尾号 2222 |
| 信用卡收到还款 | USD 100.00 |
| 短信原始汇率 | 0.147059 |
| 根据金额推得的汇率方向 | USD / CNY |

以本例金额校验，680.00 × 0.147059 = 100.00012000，按美元两位小数舍入为 100.00。这说明该示例的汇率方向为每 1 CNY 对应多少 USD。保存方向的推断依据，其他格式需单独核验。

实际转出、转入金额为记账依据，不能用已经舍入的短信汇率反算后覆盖它们。两个币种不能直接相加。“购汇转入 USD”是还款金额，不新增一个用户持有的 USD 现金账户。

关联两个账户效果后，若又收到来源借记卡的扣款短信，应给同一资金变化补充证据，不再扣款一次。没有足够关联证据时保持待确认。

这条短信只说明本次还款所用资金和汇率，不说明它对应了哪些历史消费，不提供信用卡剩余应还金额，也不能据此给所有外币消费赋予人民币结算金额。未单列的手续费、利息不擅自拆出。

## 余额连续性

合成用例可形成以下算术链：

- 54.40 − 2.00 = 52.40
- 52.40 + 2000.00 = 2052.40
- 2052.40 − 12.00 = 2040.40

这是本组样本内部的一致性检查，不证明短信完整，也不证明全天没有其他交易。余额字段可作为观察快照保存；异常只提示复核，不自动补账或改写交易时间。

## 边界用例与验收

JSON 同时包含七条合成边界输入：验证码、应还提醒、交易失败、无效千分位、无效小数、无效日期和引用交易文字的提示。这些不是声称银行实际采用的通知模板，而是解析器防止误记的测试输入。

解析实现需要：

1. 九条正例均得到所列字段；不添加样本未提供的信息。
2. 区分未识别待确认与明确非交易内容，不把子串命中当成完整模板匹配。
3. 还款两边均正确识别，RMB 统一为 CNY，原始金额及汇率精确保存。
4. 退款、撤销、重复扫描、多候选关联和还款双通知不导致重复统计。
5. 在真实接收时间、发送方信息可用后再验证 Android 接入流程。

当前解析器单测覆盖上述正例、边界和金额规则；完整验证范围见 [验证记录](verification.md)。合成测试不能代替真机验证。
