# 首版需求与记账规则

## 1. 范围与完成状态

本文件描述开发目标，不表示功能已经实现。

- 仅适配中国银行借记卡和中国银行 Visa 外币信用卡。
- 仅使用银行短信作为交易输入。
- 读取手机中仍然存在的历史短信，并处理后续新短信。
- 解析、存储和展示在设备本地完成。
- 工商银行、兴业银行及其他银行暂不适配。
- 支付宝、微信仅作为短信中可能出现的支付渠道信息，不另行同步账单。

历史范围与实际覆盖取决于手机现存短信及银行实际发送的提醒。没有收到或已经删除的短信不能靠解析补齐。

## 2. 数据分层

具体类名、数据库表和技术栈在工程阶段确定，至少区分以下概念：

| 层次 | 内容 |
| --- | --- |
| 短信来源 | 来源标识、发送方、正文、接收时间；适用时记录短信提供方的本地 ID 和 SIM 标识 |
| 解析事件 | 解析器版本、识别状态、账户线索、交易类型、精确金额、币种、商户和正文中的交易时间 |
| 关联关系 | 消费与撤销、本人账户间转账、借记卡扣款与信用卡还款等关系，以及自动或人工确认状态 |
| 展示与汇总 | 根据已识别事件及其有效关联生成列表和分类汇总，保留返回原文的入口 |

原始事件保留，修正分类或撤销关联时可恢复。重新解析不能无提示覆盖人工确认结果。

## 3. 金额、币种与时间

- 金额使用精确十进制或遵循币种精度的最小单位整数，禁止使用 Float/Double 进行金额运算。
- 存储明确的币种代码，不使用无币种的裸金额表示交易。
- `USD0.53元` → USD 0.53；`SGD1.38元` → SGD 1.38。
- 正文中的币种代码不会被结尾的“元”覆盖；人民币和 RMB 在内部规范为 CNY，并保留原文字样。
- 带千分位的金额在校验分组后解析，例如 JPY12,345 为 JPY 12345；不能先按逗号拆整条短信。
- 借记卡样本仅有月日，缺少年份且没有接收时间时保留未知年份，不直接使用程序运行年份。
- 缺少币种时，只能依据已经验证的该账户短信模板判断；无法判断则待确认。
- 原币消费额与可能出现的结算金额是不同字段。未提供的结算金额、人民币等值或汇率保持未知。
- 各币种分别汇总，不把 USD、SGD、CNY 直接相加。
- 分别记录交易时间和短信接收时间。缺少正文交易时间时可以用接收时间排序，但必须标明来源；不根据币种或商户猜测时区。

## 4. 交易分类与资金流

- 借记卡增加或减少余额，并不自动等同于收入或消费。
- 区分消费、收入、退货退款、撤销、本人账户间转账、信用卡还款及未知用途的转入转出。
- “收入(网银跨行)”只确认为资金转入；“手机银行支取(跨行支付)”只确认为资金转出，用途与对手方不明时经济分类待确认。
- “成功退货”独立记录为退款；没有商户和原消费也先保存，不把退款当作普通收入，不强制绑定同额消费。
- 购汇还款同时记录来源借记卡扣款金额、信用卡还款金额、两个币种及原始汇率；它是一笔事件的两个账户效果，不能压成单币种支出。
- 信用卡消费已经记录时，其本金还款只体现偿债及账户资金变化，不再记一笔消费。
- 明确出现的手续费、利息需要独立分类，不与还款本金混为一笔消费。
- 短信提供余额时可作为余额快照保存，不以单条通知推定完整的账户余额或信用卡负债。
- 验证码、营销、还款提醒、失败通知等非成功交易内容不直接生成消费或收入。
- 普通“消费”通知不自动标记为银行已经完成清算或入账。

## 5. 撤销与关联

短信出现“撤销”时先记录通用撤销事件；仅凭这一中文词不进一步断言它是授权撤销、入账前取消还是入账后退款。

匹配顺序：

1. 短信实际提供了可靠的原交易编号时，优先使用编号。
2. 否则结合相同账户、币种、金额、商户及时间线索生成候选。
3. 只有达到明确匹配规则且候选唯一时才自动关联，并允许用户解除关联。
4. 多个候选、账户信息缺失或原消费缺失时保持待确认。

边界行为：

| 情况 | 处理原则 |
| --- | --- |
| 全额撤销且关联确认 | 保留两条事件，关联后的有效消费金额为零 |
| 部分撤销 | 确认关联后只扣减对应金额，剩余金额仍计入有效消费 |
| 同商户、同金额多笔 | 不凭金额直接选一笔；证据不足时人工关联 |
| 撤销先于消费到达 | 暂存待匹配事件，后续重新匹配 |
| 原消费不在历史导入范围 | 保留未关联撤销，不虚构原消费 |
| 累计撤销超过原消费 | 标记异常并待确认，不产生未经解释的负消费 |
| 用户解除关联 | 恢复此前有效金额，保留操作与来源可追溯性 |

成功退货与撤销分别建模。退款发生期与原消费归属期保留各自日期，汇总时明确采用的口径，避免同时冲减原消费又重复扣减退款。购汇还款等细则见 [短信模板说明](sms-templates.md)。

## 6. 重复处理与重放

- 对同一短信来源记录建立稳定标识，确保重复扫描或重新解析不会再生成一笔交易。
- 历史读取与新短信接收共用解析和保存流程。
- 新短信广播与后续历史扫描可能观察到同一短信；实施时需定义对应策略，避免两个入口各入账一次。
- 正文哈希、金额、商户、时间只能辅助识别；不同来源记录即使正文相似，也可能对应两笔真实交易。
- 解析器版本变化时能够重放原文，并保留人工修正与关联。
- 购汇还款通知与来源借记卡扣款通知可能提供同一资金变化的不同证据。确认关联后只计一次现金扣款、一次信用卡还款；待确认关联不自动重复计入已确认汇总。

## 7. 待确认与模板验证

首版至少展示未识别模板、账户未知、币种未知、分类不确定和撤销待匹配等状态，不静默丢弃候选交易短信。

已根据九条完整短信整理七种模板形态，包括借记卡网上支付、跨行转入、跨行转出，以及信用卡消费、撤销、成功退货和购汇还款。完整结构已替换个人字段后存为 [合成解析用例](../fixtures/synthetic/boc-sms.json)。这表示已有可实施的样本规范，不表示解析器已实现或覆盖所有中行短信。

仍待 Android 接入和更多实际格式验证的项目包括：

- 正文之外的发送方号码、真实接收时间、本地短信来源标识和多段信息。
- 缺少年份日期的跨年推断及标记方式。
- 更多空格、标点和措辞变体，以及尚未观察到的通知类型。
- 同额多笔、部分撤销、退款来源缺失、还款双通知等关联场景。

卡产品名和最终结算方式不作为原币短信解析开发的前置条件。

## 8. 本地数据与仓库样本

- 应用数据默认留在设备本地。
- 不记录或上传银行登录凭据；首版没有银行登录流程。
- 调试日志避免输出完整短信、完整账号及验证码。
- 仓库示例只使用脱敏或明确标注的合成内容，真实短信与数据库不提交 Git。
- .gitignore 只是辅助措施，提交前仍需检查实际暂存内容。

## 9. 后续可评估项

余额差额检查、参考汇率折算、其他银行和额外数据来源均不计入当前首版验收范围。以后扩展时需重新确定需求。
